# RFC-001: Harness-specific features

| Field | Value |
|-------|-------|
| Status | Draft |
| Author | Scott McClung |
| Approvers | Scott McClung |

## Abstract

The marketplace compiles one shared prompt library into Claude Code, Codex and
Pi distributions, but it has no general place for code that only one harness
can run. The one existing case, the Pi model router, is handled by a hardcoded
copy step and hardcoded manifest entries. This RFC adds a second content type,
a **feature**: one capability with a native implementation per harness that
supports it, stored under `features/<name>/<harness>/`. The build discovers
features, copies each implementation into that harness's distribution, and
lists it in that harness's catalog. The first two features are the existing
Pi model router (migrated with no change to its output) and a new Claude Code
status line mod.

## Motivation

The library in `library/` is the right home for prompts, because every harness
can run a prompt once the compiler renders it with that harness's terms. Some
capabilities are not prompts, though. A Claude Code hooks module, a Pi
extension and a Codex plugin each run on their own harness's API, so they cannot
be rendered from one shared source. They still belong in the marketplace,
because the point of the marketplace is one place to install everything on a
new machine.

Today the build supports exactly one such capability, and it does so by name.
`scripts/lib/build.mjs` copies `clients/pi/extensions/` into `dist/pi/`, writes
`./extensions/model-router.mjs` into the generated Pi manifest, and writes a
single `devtools` entry into each catalog. The root `package.json` also names
the router file. Adding a second capability means editing all of those places,
and nothing in the layout says which harnesses a capability exists for.

The trigger for this RFC is a Claude Code status line mod that is ready to ship.
A Pi version of the same display is a likely next step, which makes the parity
question ("does this exist for Pi yet?") a real one that the layout should
answer.

## Goals and Non-Goals

**Goals:**

- A feature is added by creating `features/<name>/` with a `feature.json` and
  one folder per supported harness. No build script or manifest edit is needed.
- Each Claude Code feature installs on its own:
  `claude plugin install <name>@agent-marketplace`.
- Each Pi feature ships inside the existing Pi package and can be turned off
  per user through `pi config` or a package filter in Pi settings.
- Migrating the model router into `features/model-router/pi/` changes no
  generated byte except file paths and the input fingerprint.
- `npm run verify` covers features the same way it covers the library: stale or
  missing generated output fails the check.

**Non-Goals:**

- Sharing code between a feature's harness implementations. Each folder is a
  complete native implementation in that harness's own format.
- A Codex feature. The layout reserves `codex/`, and the catalog rule below
  covers it, but no Codex feature exists to validate the contract against.
- Building the Pi status line. It is a follow-up feature, not part of this work.
- Changing how the shared library compiles.

## Approaches

### Approach 1: Features grouped by capability

Each capability gets one folder, with a subfolder per harness:

```
features/
  model-router/
    feature.json
    pi/
  statusline/
    feature.json
    claude/
```

This makes parity visible, because one listing shows which harnesses a
capability supports. The shared name and description live once in
`feature.json`, so catalog entries for different harnesses cannot drift apart.
The cost is a new top-level folder, and the harness folders inside it do not sit
next to that harness's `clients/` config. Effort: medium.

### Approach 2: Native plugins grouped by harness

Each harness gets a plugins folder next to its existing config:

```
clients/
  claude/plugins/statusline/
  pi/extensions/model-router/
```

This is closer to today's layout, since `clients/pi/extensions/` already
exists, and someone working on one harness finds everything for it in one
place. The cost shows up once a capability exists for two harnesses: its two
implementations live in unrelated folders, its description is written twice,
and nothing ties them together. Answering "what do we have for Pi but not
Claude" means comparing directory listings. Effort: small.

### Approach 3: Bundle native code into each harness's main plugin

The build copies native code into the existing `devtools` distribution for that
harness, so the status line ships inside the Claude `devtools` plugin.

This needs no catalog changes and keeps one install per harness, which is the
simplest experience for a single user. The cost is that every `devtools` install
gets every feature with no way to opt out on Claude Code, and a UI mod becomes
part of a plugin whose purpose is the prompt library. Effort: small.

### Recommendation

We recommend Approach 1. The status line is the first capability likely to
exist for two harnesses, and Approach 1 is the only layout where that is a
single unit with one description. We give up the "everything for Pi in one
folder" view that Approach 2 offers, and we accept a new top-level folder.
Approach 3 lost because optional installs matter more than one fewer catalog
entry, especially for a UI change that some machines may not want.

## Detailed Design

### Architecture changes

```
                 package.json (version)
                         │
 library/  clients/      │      features/<name>/feature.json
    │         │          │          │
    │         │          │          ├── claude/  ─────────┐
    │         │          │          ├── pi/      ───────┐ │
    │         │          │          └── codex/ (future) │ │
    ▼         ▼          ▼                              │ │
 ┌─────────────────────────────────────────────┐        │ │
 │ scripts/lib/build.mjs                       │◀───────┴─┘
 │   compile library        (unchanged)        │
 │   [NEW] discoverFeatures(root)              │
 │   [NEW] emitClaudeFeature / emitPiFeature   │
 │   [CHANGED] catalogs and Pi manifest built  │
 │             from the discovered list        │
 └─────────────────────────────────────────────┘
          │                 │                │
          ▼                 ▼                ▼
 dist/claude/      dist/claude-plugins/   dist/pi/extensions/
 (devtools)        <name>/  [NEW]         <name>/  [CHANGED]
          │                 │
          ▼                 ▼
 .claude-plugin/marketplace.json: devtools + one entry per Claude feature
```

*The build reads features beside the library and emits each implementation into
its harness's distribution and catalog.*

The library pipeline does not change. Feature handling runs after it, so a
feature cannot affect how prompts render.

### Feature manifest

`feature.json` holds what every harness's catalog entry shares:

```json
{
  "name": "statusline",
  "description": "Repo, commits, model, context use, cost and reset timer under the prompt"
}
```

The build fails when `name` does not match the folder name, when it is not a
lowercase hyphenated identifier, when it collides with `devtools`, or when the
feature has no harness folder. Unknown harness folders also fail, so a typo
like `claud/` is caught instead of silently skipped.

### Claude Code features

A `claude/` folder is a complete Claude Code plugin, so `claude plugin validate`
and `claude plugin test` work on it directly during development. The build
copies it to `dist/claude-plugins/<name>/` with two changes:

- `.claude-plugin/plugin.json` gets `version` set from the root `package.json`,
  so every distribution in a release carries the same version. The build fails
  when its `name` differs from the feature name.
- `*.test.ts` and `*.test.tsx` files are left out. They only run under
  `claude plugin test` against the source folder, and installed copies have no
  use for them.

`.claude-plugin/types/` is written by Claude Code itself whenever it loads a
mod, so it is ignored in Git and never copied. Each Claude feature adds one
catalog entry:

```json
{ "name": "statusline", "source": "./dist/claude-plugins/statusline", "description": "..." }
```

### Pi features

Pi installs a Git repository as one package, defined by the root `package.json`.
Pi features therefore ship inside that package rather than as separate
installs. Users who do not want one turn it off with `pi config`, or with an
`extensions` filter on the package entry in Pi settings, which Pi supports for
any package's declared resources.

Each `pi/` folder is copied to `dist/pi/extensions/<name>/` byte for byte,
keeping the current rule that extension assets are opaque and never templated.
Its entry point must be `index.mjs`, which lets both manifests use one glob
instead of naming each feature:

| Manifest | Owner | `pi.extensions` |
|----------|-------|-----------------|
| Root `package.json` | Hand-written source | `["./dist/pi/extensions/*/index.mjs"]` |
| `dist/pi/package.json` | Generated | `["./extensions/*/index.mjs"]` |

The root manifest stays hand-written because the build does not own
`package.json`. With the glob it no longer changes when a Pi feature is added,
and a build test asserts the glob is present.

### Model router migration

`clients/pi/extensions/model-router.mjs` becomes
`features/model-router/pi/index.mjs`, and `model-router.json` moves beside it.
The router loads its defaults with `new URL('./model-router.json',
import.meta.url)`, a path relative to itself, so the move needs no code change.
`clients/pi/extensions/` is then removed, and the build no longer reads it.

The installed path changes from `extensions/model-router.mjs` to
`extensions/model-router/index.mjs`. Anyone with a Pi settings filter naming the
old path has to update it. Today that is only the owner.

## Build Guarantees

This system has no service, so the equivalents of SLAs are guarantees the build
makes and `npm run verify` enforces.

| Guarantee | How it is checked |
|-----------|-------------------|
| Same inputs give byte-identical output | Existing `--check` comparison |
| Every feature file is part of the input fingerprint | Build test changes a feature byte and expects a new `inputsDigest` |
| Feature output appears only under owned roots | Existing `emit` path guard |
| Pi feature assets are copied unchanged | Byte comparison test, generalized from the router test |
| Router migration changes no router bytes | One-time check that each router file in `dist/` matches its pre-migration bytes |

## Security Considerations

Features run code on the user's machine with that harness's permissions. The
status line runs `git` and reads files under `~/.claude`. The router reads Pi
credentials. Nothing changes about that compared with installing them by hand,
but grouping them in a catalog makes them easier to install without reading.
Two existing harness protections still apply: Claude Code only loads hooks
modules after workspace trust is accepted, and Pi only loads project packages
after project trust. Feature folders get the same review standard as
`library/` changes, and each feature's README states what it runs and reads.

## Testing & Rollout

### Test plan

Build tests in `test/build.test.mjs` cover discovery, validation errors, catalog
entries, the Pi manifest glob, opaque copying, test-file exclusion, and the
fingerprint. These run under `npm test` with no harness installed, which keeps
the repository rule that tests make no model requests and touch no personal
configuration.

Each feature also keeps its native tests. For Claude features that means
`claude plugin test features/<name>/claude`. A smoke check installs the built
catalog into a temporary Claude Code config directory and confirms the feature
plugin is listed and loads, following the existing rule of using temporary
client homes for install checks.

### Rollout plan

1. Add feature discovery and move the model router. `dist/` differs only in
   router paths and the fingerprint, which confirms the refactor.
2. Add `features/statusline/claude/` from `~/.claude/mods/statusline`, build,
   and run the temporary-home install smoke check.
3. On each machine, install `statusline@agent-marketplace`, then remove the
   `CLAUDE_CODE_PLUGIN_DIRS` entry from `~/.claude/settings.json` so the mod
   does not load twice.

### Rollback plan

Each step is one commit. Reverting step 2 removes the status line from the
catalog, and an installed copy keeps working until it is uninstalled. Reverting
step 1 restores `clients/pi/extensions/` and the hardcoded entries. Roll back if
`npm run verify` cannot be made to pass, or if the migrated router behaves
differently in Pi.

## Observability

There is no runtime system to monitor. Build failures name the feature and the
rule it broke, for example `features/statusline/feature.json: name "status-line"
does not match folder "statusline"`. `dist/manifest.json` gains a feature count
per harness, so a missing feature shows up in its diff.

## Open Questions

**Should `npm run verify` run each feature's native tests?** Running them would
catch a broken feature before release, but it would require `claude` (and later
`pi`) on any machine or CI runner that verifies. Leaning: keep `verify`
harness-free, and add `npm run test:features`, which runs native tests for each
harness whose CLI is installed and reports the ones it skipped.

**Should a feature's version follow the library version?** One version keeps
releases simple and matches how the three distributions work today. It also
means a status line change bumps the prompt library version. Leaning: one
version for now, revisited if features start releasing on their own schedule.
